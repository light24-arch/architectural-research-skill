# 建筑前期研究

从项目理解与取证推进到问题、设计机会和具体空间动作。资料不足时保留缺口，不为完成模板制造事实。

## 范围与优先级

用户当前明确要求 → 本任务已确认偏好 → 现有资料结构 → 模式默认值。
任务书是证据输入，不自动授权完整调研。先确定所需成果，再选择最小且完整的研究范围。

| 模式 | 选择条件 | 成果 |
|---|---|---|
| 完整研究 | 要求整套前期调研 | 用户选择形式的调研文档、备选设计方向与空间策略；HTML 演示另行选择 |
| 专题研究 | 指定气候、人群、交通等问题 | 专题分析与空间启示 |
| 案例库 | 寻找、整理或比较参考项目 | 案例、索引与比较 |
| 研究补充 | 修改或补充既有成果 | 指定缺口与关联文件更新 |

详细完成标准与边界读取 [task-modes.md](references/task-modes.md)。混合任务组合所需部分，不叠加整套模板。

## 工作顺序

1. 收到任务书后，先向用户确认本项目属于课程设计、实际项目还是竞赛作品；按下节记录项目类型。
2. 读取任务书、用户材料与现有成果，确定研究任务模式，按 [project-types.md](references/project-types.md)
   校正该类型的研究重点、分析深度和验证方式，简述问题、证据与重要缺口。
   开始取证时读 [evidence-quality.md](references/evidence-quality.md)，再按下表加载研究内容。
3. 研究针对能改变设计判断的证据缺口；完整调研后提出数个有差异的可能设计方向，
   分别说明重点问题与所需分析，再关联具体空间策略。执行 [design-directions.md](references/design-directions.md)。
4. 研究内容整理完成、正式渲染前让用户选择主文档交付形式，再加载选定格式指南、检查并交付。
   主文档交付后询问是否需要 HTML 演示文件，遵循“输出选择与模板使用”。

已确认的范围、格式与组织方式不重复询问。只有缺项会改变研究目标、地理范围、必需成果或关键结论
有效性时提问，同时推进独立工作；其他缺项标注后继续。用户修正更新当前任务，不重做全部初始化。
使用用户指定或环境实际可用的文档读取工具；工具不可用时保留已完成内容并说明限制。

位置纠正、用户筛选、候选转入库和跨文档更新，先读
[research-maintenance.md](references/research-maintenance.md)，再取证或修改；以当前场地和文件状态为准。

### 启动：确认项目类型

- 对新研究项目，在收到任务书后询问：“这个项目属于课程设计、实际项目，还是竞赛作品？”
  这是研究用途分类，不是建筑功能类型，也不是完整研究/专题/案例库/补充的任务模式。
- 若用户在本任务已明确项目类型，复述并记录即可，不重复要求选择；不凭文件名、学校署名或内容自行确定。
- 等待回答时可读取材料、盘点证据和缺项；依赖项目类型的侧重点安排待回答后开展，不擅自选一个类型。
- 在项目概况/工作摘要中记录类型及其确认状态；类型纠正时更新相关研究安排，保留可复用的研究成果。
- 确认类型后读取 [project-types.md](references/project-types.md)：课程设计关注问题形成、空间推演与论证；
  实际项目关注真实需求、可行性、实施与使用；竞赛关注命题、独特贡献及空间与表达的一致性。
  类型作初步排序，任务书和用户目标校正；保持共同证据标准，不固定权重、篇幅或强制分析清单。
  交叉用途组合相关要求，实施型竞赛叠加有关可行性分析，不扩大所选任务模式的范围。

### 连续指令：先定位修改对象

- 根据最近的要求、当前成果与已确认对象，定位具体文件／章节，再简述修改范围；上下文明确直接继续。
- 区分维护技能和研究建筑项目；指代仍有两种实质解释时，只问会改变修改对象的关键问题。
- 用户纠正时更新对象并撤回受影响的误改，保留有效研究；按已授权的先后任务完成，不重复初始化。

## 输出选择与模板使用

主文档不默认采用 Obsidian、Markdown 或 HTML。研究内容整理完成、正式渲染前，
向用户提供 Obsidian、飞书文档、DOCX 文档三个选择，简述用途并等待选择后生成选定成果。
启动时可介绍选项；用户可提前指定。已有本任务明确选择或明确要求在原文中补充时沿用，不重复询问；
旧成果的格式只能作参考，不能把它当作新研究的自动选择。选择不会扩大研究范围或重做已完成分析。

| 主文档选项 | 交付内容 |
|---|---|
| Obsidian | 可导航、可关联的 Markdown 档案与所需附件；沿用已认可案例库的组织习惯 |
| 飞书文档 | 可在线阅读、协作与补充的文档链接；需实际可用连接与对应写入授权 |
| DOCX 文档 | 可编辑的 Word 调研文档，按文档技能完成排版与检验 |

只有用户选择 Obsidian 才按档案规则组织。其具体分区、拆分粒度、字段与附件组织仍待讨论；
首次实施前明确影响组织的选择，已确认结构直接沿用。不要强制把九模块拆成九个文件。
飞书连接不可用时说明并保留本地可编辑内容，提供其他可用选项，不能把替代草稿宣称为飞书交付成功。

主文档输出并交付链接/文件后，再询问：“是否需要基于这份调研文档生成 HTML 演示文件？”
用户答需要后制作；未答不自动生成。若本任务已明确需要或不要 HTML，沿用该决定，不重复询问，
但仍先完成主文档，再制作已请求的演示文件。HTML 复用已交付内容及证据，不重新启动研究。
HTML 是第二阶段可选演示，不列为本轮主文档的第四选项；它不是默认主文档或默认附赠成果。
新完整报告文件名为 `<项目名称>_前期研究报告` 加选定扩展名；现有成果沿用命名和结构。

[research-book-template.html](assets/research-book-template.html) 只用于新完整 HTML 报告的起始布局。
它是占位骨架，不是证据或内容规则；只在制作 HTML 时读取/复制，不用于专题或案例库强加九模块。
章节、策略数量及证据状态来自对应参考文件。修改目录和内容时同步锚点，交付前替换占位或说明缺口。
模板未包含的组件/交互按 HTML 指南与任务需要实现，不能仅复制骨架就声称全部功能已完成。

## 交付检查

- 修改对象符合最近明确的上下文；项目类型已确认，研究重点与阶段符合任务书；范围符合请求。
- 类型侧重点落实到问题、案例阅读、方向分析与下一步，而不只是报告标签；交叉用途按 project-types.md 组合。
- 主文档形式是用户选择，先交付主文档再询问 HTML；参考文件只加载与任务有关的部分。
- 事实、推断、待核实可区分，来源内容支持关联结论；具体检查遵循 evidence-quality.md。
- 章节引用、策略要素、数量、锚点和索引一致；内容规则遵循 report-structure.md，不以模板覆盖。
- 图像与计算口径可追溯，未运行的工具和未核验数据不包装成成果。
- 当前案例文件、正式数量与候选状态一致；重大更正同步其依赖结论，深读程度与实际取得资料一致。
- 策略具体、有区别、成立条件清楚，并给出下一步验证方法。
- 完整研究的备选方向有实质差异；每个重点问题对应分析材料、方法/成果和设计决定，未做分析明确标为计划。
